\chapter{Design and Modeling}

\section{Introduction}

After defining the actors and requirements in the previous chapter, we now move to the design phase of the Stag.io platform. The objective of this chapter is to translate the functional analysis into structural and behavioral models that clarify how the system is organized and how its main workflows are executed.

This chapter is structured around several complementary views. We first present the class diagram that captures the principal domain entities and their associations. We then introduce the navigation diagram to explain how users move through the interface according to their role. After that, we analyze the dynamic behavior of the platform through three activity diagrams and four sequence diagrams. Finally, we conclude with the relational model that formalizes the persistence layer used by the PostgreSQL database.

\section{Class Diagram}

The class diagram provides a static view of the system by identifying the main business entities, their attributes, and the associations that connect them. In Stag.io, the \texttt{User} entity forms the core of the model, while \texttt{Student}, \texttt{Company}, and \texttt{University} provide role-specific profiles. The operational center of the platform is built around internship offers, applications, reviews, saved offers, and notifications.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.88\textheight,keepaspectratio]{2-class-diagram.png}
\caption{Class diagram of the Stag.io platform}
\label{fig:class-diagram}
\end{figure}

The diagram highlights the following design decisions:

\begin{itemize}
    \item A single \texttt{User} table centralizes authentication data, identity information, and the role assigned to each account.
    \item Role-specific information is isolated into dedicated entities (\texttt{Student}, \texttt{Company}, \texttt{University}) linked one-to-one to \texttt{User}.
    \item The core internship lifecycle is modeled through the chain \texttt{Company} $\rightarrow$ \texttt{InternshipOffer} $\rightarrow$ \texttt{Application}.
    \item Complementary services such as bookmarks, notifications, and reviews are represented by autonomous entities linked to the main operational flow.
\end{itemize}

\section{Relational Model}

The relational model translates the conceptual design into a database structure that can be implemented in PostgreSQL. Figure~\ref{fig:relational-model} presents the core persistence schema used by Stag.io. For readability, the audit log table is omitted from the figure, but it remains part of the physical database schema.

\begin{figure}[H]
\centering
\includegraphics[width=\textwidth,height=0.88\textheight,keepaspectratio]{9-relational-model.png}
\caption{Core relational model of the Stag.io database}
\label{fig:relational-model}
\end{figure}

This relational organization enforces the main business rules of the application:

\begin{itemize}
    \item A user can own at most one student, company, or university profile through a one-to-one relationship.
    \item A company can publish multiple internship offers, while each offer belongs to exactly one company.
    \item A student can submit multiple applications, but each application references a single internship offer.
    \item The tables \texttt{applications} and \texttt{saved\_offers} implement uniqueness constraints to prevent duplicate submissions and duplicate bookmarks.
    \item Reviews are linked to validated internship experiences through the \texttt{applications} table, ensuring traceability of post-internship feedback.
\end{itemize}

\section{Conclusion}

In this chapter, we transformed the functional requirements of Stag.io into a coherent design model. The class diagram clarified the structural organization of the domain, the navigation diagram outlined the principal user paths, and the activity and sequence diagrams explained the runtime behavior of the system for the most important workflows.

We also presented the relational model that underpins data persistence in PostgreSQL and enforces the essential business constraints of the platform. Together, these models provide a consistent technical blueprint for the implementation of Stag.io and establish the foundation for the architectural and implementation choices presented in the following stages of the project.
