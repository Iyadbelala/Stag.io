\section{Key Implementation Details}

In this section, we present the implementation of the platform's most distinctive features: the SmartMatch recommendation engine, the real-time notification system, and the security mechanisms.

\subsection{SmartMatch Recommendation Engine}

The SmartMatch engine is the core differentiator of Stag.io. Unlike traditional platforms that display offers in chronological order, SmartMatch computes a relevance score for each offer based on four dimensions of the student's profile. The final composite score is computed using the following weighted formula:

\[
\text{Score}_{\text{final}} = 0.50 \times S_{\text{skills}} + 0.25 \times S_{\text{dept}} + 0.15 \times S_{\text{loc}} + 0.10 \times S_{\text{title}}
\]

where each component score is normalized to the range $[0, 1]$, and the final result is expressed as a percentage from 0 to 100.

\subsubsection{Skill Matching (50\% Weight)}

The skill matching function compares the student's declared skills against the offer's requirements and description. It supports both exact matching (when the full skill name appears in the text) and partial matching (when individual words of a multi-word skill appear). Partial matches are weighted at 70\% of the full match value, ensuring that broad skills like ``Machine Learning'' can still match offers that mention individual keywords.

\begin{figure}[H]
\begin{lstlisting}[language=JavaScript]
export function scoreSkills(
  studentSkills: string[],
  requirements: string,
  description: string,
): { score: number; matchedSkills: string[] } {
  if (studentSkills.length === 0) return { score: 0, matchedSkills: [] };
  const offerText = norm(requirements + ' ' + description);
  const matchedSkills: string[] = [];
  let totalWeight = 0;

  for (const skill of studentSkills) {
    const skillNorm = norm(skill);
    if (offerText.includes(skillNorm)) {
      matchedSkills.push(skill);
      totalWeight += 1.0;
    } else {
      const words = skillNorm.split(' ');
      const partialHits = words.filter(
        w => w.length > 2 && offerText.includes(w));
      if (partialHits.length > 0) {
        const ratio = partialHits.length / words.length;
        if (ratio >= 0.5) {
          matchedSkills.push(skill);
          totalWeight += ratio * 0.7;
        }
      }
    }
  }

  const reqTokens = requirements.split(/[,;/\n]+/)
    .map(t => t.trim()).filter(t => t.length > 1);
  const normFactor = Math.min(
    Math.max(reqTokens.length, 1), studentSkills.length);
  const score = matchedSkills.length > 0
    ? Math.min(totalWeight / normFactor, 1.0) : 0;
  return { score, matchedSkills };
}
\end{lstlisting}
\caption{Implementation of the skill matching function (50\% weight)}
\label{fig:code-skills}
\end{figure}

\subsubsection{Department Relevance (25\% Weight)}

The department scoring function maps academic departments to industry-relevant keywords. A pre-built dictionary covers 17 academic domains (Computer Science, Business, Medicine, Law, Design, etc.), each associated with 10--20 industry keywords. The function measures how many of these keywords appear in the offer text to determine the relevance between the student's field of study and the internship content. When no department is provided, the function returns a neutral score of 0.3 to avoid penalizing students with incomplete profiles.

\subsubsection{Location Matching (15\% Weight)}

The location scorer extracts city-level information from the student's university domain (e.g., extracting ``constantine'' from \texttt{univ-constantine2.dz}) and compares it against the offer's location and the company's headquarters. An exact city match returns a score of 1.0, remote offers receive 0.7 (as they are location-agnostic), and completely unmatched locations receive 0.1.

\subsubsection{Title Relevance (10\% Weight)}

The title relevance function checks whether the student's skills appear in the offer title, providing a heuristic for job-title alignment. The score is capped at 1.0 and normalized by the smaller of the student's skill count and three, ensuring that students with many skills are not unfairly disadvantaged.

\subsubsection{Orchestration and Ranking}

The main matching function orchestrates the entire pipeline: it retrieves the student profile and all active offers from the database, computes the four component scores for each offer, applies the weighted formula, sorts the results by descending score, and returns the top $n$ matches. The entire computation executes in under 100\,ms per request, meeting the performance requirements specified in Chapter~2.

\subsection{Real-Time Notification System}

The platform uses Socket.IO to deliver instant notifications to connected users. When a triggering event occurs (e.g., application status change, new application received, agreement pending validation), the backend persists the notification in the database and simultaneously pushes it to the user's browser through a dedicated WebSocket room.

\begin{figure}[H]
\begin{lstlisting}[language=JavaScript]
export async function sendNotification(
  userId: string,
  type: 'application_status_changed' | 'new_application'
    | 'agreement_needs_validation'
    | 'company_pending_approval'
    | 'university_pending_approval',
  title: string,
  message: string,
  relatedId?: string,
): Promise<NotificationData> {
  const [notification] = await db.insert(notifications).values({
    userId, type, title, message,
    relatedId: relatedId ?? null,
  }).returning();

  // Push real-time notification via WebSocket
  try {
    getIO().to(userId).emit('notification', {
      id: notification.id,
      userId: notification.userId,
      type: notification.type,
      title: notification.title,
      message: notification.message,
      isRead: notification.isRead,
      relatedId: notification.relatedId,
      createdAt: notification.createdAt.toISOString(),
    });
  } catch { /* Socket.io may not be initialized in tests */ }

  return data;
}
\end{lstlisting}
\caption{Real-time notification dispatch via Socket.IO}
\label{fig:code-notification}
\end{figure}

On the client side, the Socket.IO connection is authenticated using the JWT access token passed during the WebSocket handshake. Each user is automatically joined to a private room identified by their user ID, ensuring that notifications are delivered exclusively to the intended recipient.

\begin{figure}[H]
\begin{lstlisting}[language=JavaScript]
export function initSocket(httpServer: HttpServer): Server {
  io = new Server(httpServer, {
    cors: {
      origin: (process.env.CLIENT_URL || 'http://localhost:3000')
        .replace(/\/+$/, ''),
      credentials: true,
    },
  });

  io.on('connection', (socket) => {
    const token = socket.handshake.auth.token;
    if (!token) { socket.disconnect(); return; }

    try {
      const payload = jwt.verify(
        token, process.env.JWT_SECRET!) as JwtPayload;
      socket.join(payload.sub); // Join user-specific room
    } catch {
      socket.disconnect();
    }
  });

  return io;
}
\end{lstlisting}
\caption{WebSocket server initialization with JWT-authenticated rooms}
\label{fig:code-socket}
\end{figure}

\subsection{Security Implementation}

The security layer of Stag.io implements several defense-in-depth mechanisms to protect user accounts and API endpoints.

\subsubsection{Account Lockout Mechanism}

To prevent brute-force attacks, the system implements an in-memory account lockout tracker. After five consecutive failed login attempts, the account is locked for 15 minutes. The counter is automatically reset upon successful authentication. A periodic cleanup routine runs every five minutes to evict expired lockout records from memory.

\begin{figure}[H]
\begin{lstlisting}[language=JavaScript]
const MAX_ATTEMPTS = 5;
const LOCKOUT_DURATION_MS = 15 * 60 * 1000; // 15 minutes

const attempts = new Map<string, AttemptRecord>();

export function recordFailedAttempt(email: string): boolean {
  const key = email.toLowerCase();
  const record = attempts.get(key)
    ?? { count: 0, lockedUntil: null };
  record.count += 1;

  if (record.count >= MAX_ATTEMPTS) {
    record.lockedUntil = Date.now() + LOCKOUT_DURATION_MS;
    attempts.set(key, record);
    return true; // Account is now locked
  }

  attempts.set(key, record);
  return false;
}

export function isAccountLocked(email: string): number {
  const key = email.toLowerCase();
  const record = attempts.get(key);
  if (!record?.lockedUntil) return 0;

  const remaining = record.lockedUntil - Date.now();
  if (remaining <= 0) { attempts.delete(key); return 0; }
  return Math.ceil(remaining / 1000);
}
\end{lstlisting}
\caption{Account lockout mechanism for brute-force protection}
\label{fig:code-lockout}
\end{figure}

\subsubsection{JWT Token Management and Blacklisting}

The authentication flow relies on short-lived access tokens (15 minutes) and long-lived refresh tokens (7 days) with full token rotation on each refresh. Upon logout, the current access token is added to an in-memory blacklist indexed by its expiration time, preventing its reuse during the remaining validity window. A periodic cleanup routine removes expired entries to prevent memory leaks.

\section{Database Structure and Data Implementation}

The application handles a multitude of interconnected data sets governing users, internships, and dynamic features like notifications and reviews.

\subsection{Database Structure}

The database structure maps exactly to the relational model envisioned during the design phase in Chapter~3. It utilizes PostgreSQL as the primary persistence engine, hosted on Neon Cloud for serverless scalability. The schema heavily depends on relational constraints (\texttt{FOREIGN KEY}, \texttt{UNIQUE}, \texttt{ON DELETE CASCADE}) to naturally maintain data integrity between companies, their offers, and the student applications.

\subsection{Implementation of Data and Processing}

To manipulate this data structure from our backend, we implemented Drizzle ORM --- a TypeScript-first ORM that provides compile-time type safety across all database queries. Below is an example snippet showing how the \texttt{users} and \texttt{internship\_offers} data structures are translated into pure TypeScript schema definitions.

\begin{figure}[H]
\begin{lstlisting}[language=JavaScript]
import { pgTable, text, boolean, timestamp, pgEnum }
  from 'drizzle-orm/pg-core';
import { createId } from '@paralleldrive/cuid2';

export const userRoleEnum = pgEnum('UserRole',
  ['student', 'company', 'admin', 'university']);

export const users = pgTable('users', {
  id: text('id').primaryKey()
    .$defaultFn(() => createId()),
  email: text('email').notNull().unique(),
  passwordHash: text('passwordHash').notNull(),
  role: userRoleEnum('role').default('student').notNull(),
  isEmailVerified: boolean('isEmailVerified')
    .default(false).notNull(),
  createdAt: timestamp('createdAt', { withTimezone: true })
    .defaultNow().notNull(),
});

export const internshipOffers = pgTable('internship_offers', {
  id: text('id').primaryKey()
    .$defaultFn(() => createId()),
  companyId: text('companyId').notNull()
    .references(() => companies.id, { onDelete: 'cascade' }),
  title: text('title').notNull(),
  status: text('status').default('active').notNull(),
  createdAt: timestamp('createdAt', { withTimezone: true })
    .defaultNow().notNull(),
});
\end{lstlisting}
\caption{Data modeling with Drizzle ORM (TypeScript schema definition)}
\label{fig:code-schema}
\end{figure}

This schema-as-code approach ensures that any change to the database structure is versioned, reviewable, and automatically reflected in the TypeScript types used throughout the application.
